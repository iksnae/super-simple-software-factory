# Chapter 22: The Clean Architecture

## Core Idea
Hexagonal Architecture, DCI, and BCE all achieve the same separation of concerns by layering; integrating them yields concentric circles governed by one overriding rule — **source code dependencies must point only inward, toward higher-level policies**.

## Frameworks Introduced
- **The three antecedents**:
  - **Hexagonal Architecture** (Ports and Adapters), developed by **Alistair Cockburn**, adopted by Steve Freeman and Nat Pryce in *Growing Object Oriented Software with Tests*
  - **DCI** from **James Coplien and Trygve Reenskaug**
  - **BCE** from **Ivar Jacobson**, *Object Oriented Software Engineering: A Use-Case Driven Approach*
  - "Although these architectures all vary somewhat in their details, they are very similar. They all have the same objective, which is **the separation of concerns**. They all achieve this separation by dividing the software into layers. Each has at least one layer for business rules, and another layer for user and system interfaces."
- **The Dependency Rule**: *"Source code dependencies must point only inward, toward higher-level policies."*
  - "Nothing in an inner circle can know anything at all about something in an outer circle. In particular, **the name of something declared in an outer circle must not be mentioned by the code in an inner circle**. That includes functions, classes, variables, or any other named software entity."
  - And it extends to data: "**data formats declared in an outer circle should not be used by an inner circle**, especially if those formats are generated by a framework in an outer circle."
- **Crossing boundaries against the flow of control**: "suppose the use case needs to call the presenter. This call must not be direct because that would violate the Dependency Rule... So we have the use case call an interface (the **use case output port**) in the inner circle, and have the presenter in the outer circle implement it."
  - "We take advantage of **dynamic polymorphism** to create source code dependencies that oppose the flow of control so that we can conform to the Dependency Rule, **no matter which direction the flow of control travels**."
- **Which data crosses the boundaries**: "simple data structures. You can use basic structs or simple data transfer objects if you like. Or the data can simply be arguments in function calls. Or you can pack it into a hashmap, or construct it into an object."
  - "**We don't want to cheat and pass Entity objects or database rows.**" A database framework's convenient "row structure" must not be passed inward — "Doing so would violate the Dependency Rule because it would force an inner circle to know something about an outer circle."
  - "When we pass data across a boundary, it is always in the form that is **most convenient for the inner circle**."

## Key Concepts
- **The five characteristics these architectures produce**:
  1. **Independent of frameworks** — "does not depend on the existence of some library of feature-laden software. This allows you to use such frameworks as tools, rather than forcing you to cram your system into their limited constraints."
  2. **Testable** — "The business rules can be tested without the UI, database, web server, or any other external element."
  3. **Independent of the UI** — "A web UI could be replaced with a console UI, for example, without changing the business rules."
  4. **Independent of the database** — "You can swap out Oracle or SQL Server for Mongo, BigTable, CouchDB, or something else."
  5. **Independent of any external agency** — "your business rules don't know anything at all about the interfaces to the outside world."
- **The four circles are schematic, not mandatory**: "You may find that you need more than just these four. There's no rule that says you must always have just these four. **However, the Dependency Rule always applies.**"
- **The gradient**: "The outer circles are **mechanisms**. The inner circles are **policies**." Moving inward, "the level of abstraction and policy increases. The outermost circle consists of low-level concrete details... The innermost circle is the most general and highest level."

## Reference Tables

The four circles, outermost to innermost:

| Circle | Contains | Changes when… | Notes |
|---|---|---|---|
| **Frameworks and Drivers** | The database, the web framework, tools | Externals change | "Generally you don't write much code in this layer, other than **glue code** that communicates to the next circle inward." **"The web is a detail. The database is a detail. We keep these things on the outside where they can do little harm."** |
| **Interface Adapters** | Presenters, Views, Controllers — "**this layer will wholly contain the MVC architecture of a GUI**"; database gateway implementations; adapters for external services | The external format changes | "If the database is a SQL database, then **all SQL should be restricted to this layer**." Models "are likely just data structures passed from the controllers to the use cases, and then back from the use cases to the presenters and views." |
| **Use Cases** | Application-specific business rules; all the use cases of the system | The operation of the application changes | "These use cases orchestrate the flow of data to and from the entities, and direct those entities to use their Critical Business Rules." Not affected by database, UI, or framework changes. |
| **Entities** | Enterprise-wide Critical Business Rules | Almost never | "An entity can be an object with methods, or it can be a set of data structures and functions... so long as the entities can be used by many different applications in the enterprise." Without an enterprise, "these entities are the business objects of the application." **"No operational change to any particular application should affect the entity layer"** — not page navigation, not security. |

## Worked Example
**A typical scenario: web-based Java, with a database, traced end to end.**

Follow both the flow of control and the source code dependencies — they run in opposite directions at every boundary, which is the entire point.

1. **The web server** gathers input data from the user and hands it to the **Controller**.
2. **The Controller** packages that data into a **plain old Java object** — note: not an `HttpRequest`, not a framework type — and passes it through the **InputBoundary** interface to the **UseCaseInteractor**.
3. **The UseCaseInteractor** interprets the data and "uses it to **control the dance of the Entities**." It also uses the **DataAccessInterface** to bring the data those Entities need into memory from the **Database**.
4. On completion, the Interactor gathers data from the Entities and constructs **OutputData** — "another plain old Java object."
5. **OutputData** passes through the **OutputBoundary** interface to the **Presenter**.
6. **The Presenter** repackages OutputData into a **ViewModel**, "yet another plain old Java object," containing "mostly Strings and flags that the View uses to display the data."
   - Where OutputData "may contain `Date` objects, the Presenter will load the ViewModel with corresponding **Strings already formatted properly for the user**. The same is true of `Currency` objects or any other business-related data."
   - "**Button and MenuItem names are placed in the ViewModel**, as are flags that tell the View whether those Buttons and MenuItems should be gray."
7. **The View** is left "with almost nothing to do other than to move the data from the ViewModel into the HTML page."

**Now read the arrows.** Control flows outer → inner → outer: web server → Controller → Interactor → Entities → Interactor → Presenter → View. But **every source code dependency crosses its boundary pointing inward**. The Controller depends on `InputBoundary`; the Interactor owns it. The Presenter depends on `OutputBoundary`; the Interactor owns that too, and calls it without ever naming the Presenter. The Interactor depends on `DataAccessInterface`; the database layer implements it.

Three things fall out of this trace worth noting:

- **Formatting is an outward concern.** A `Date` becomes a formatted `String` in the Presenter, not in the Interactor — because the format the user wants is a detail, and the Interactor may not know one.
- **Even greyed-out buttons are ViewModel data.** The decision that a button is disabled is application policy; *rendering* it grey is not. The boolean crosses outward; the rendering stays outside.
- **Nothing framework-shaped crosses inward.** Three separate plain-old-Java-objects exist (input data, OutputData, ViewModel) precisely so that no `HttpRequest`, no ORM row, and no widget type ever reaches an inner circle.

**The payoff Martin states plainly**: "By separating the software into layers and conforming to the Dependency Rule, you will create a system that is **intrinsically testable**, with all the benefits that implies. When any of the external parts of the system become obsolete, such as the database, or the web framework, you can replace those obsolete elements **with a minimum of fuss**."

## Key Takeaways
1. Hexagonal, DCI, and BCE converge on the same idea; the Clean Architecture integrates them into one diagram.
2. The Dependency Rule is the whole architecture: source dependencies point only inward, and inner circles may not name anything outer — including data formats.
3. Four circles is a schematic, not a law; the number can vary, the rule cannot.
4. Cross boundaries against the flow of control with output ports implemented by outer-circle classes.
5. Only simple, dependency-free data structures cross boundaries — never Entities, never database rows.
6. Data always crosses in the form most convenient for the *inner* circle.
7. MVC lives entirely in the interface adapters layer, and all SQL lives in the database part of that layer.
8. The result is testable without UI, database, or web server, and lets obsolete externals be replaced with minimum fuss.
